# OpenCode iPhone client lifecycle research

Research date: 2026-09-13. OpenCode source baseline: released v1.18.30, commit [`3104c1428ec91f809e5ab86631300de41eb6952e`](https://github.com/anomalyco/opencode/commit/3104c1428ec91f809e5ab86631300de41eb6952e). This report is research only; no OpenCode process, private data, or configuration was touched.

## Decision

An iPhone SwiftUI client can be a direct client of the existing OpenCode server over Tailscale for foreground use. The initial implementation candidate should be the documented legacy API: `POST /session/:sessionID/prompt_async`, legacy message/status reads, and `GET /event` for live hints. The released tree also contains an experimental V2 HttpApi with durable prompt admission and replay, but route existence alone does not prove that the installed `opencode serve` is running the V2 execution path; keep V2 as a separately gated compatibility spike rather than implementing both protocols in the first client.

The official app detector probes `/global/health` first and classifies a healthy response as V1; it probes `/api/health` only afterward, classifying a numeric `pid` response as V2 and a healthy-only response as V1. This means one release can expose `/api` routes while the app still selects the V1 protocol. The detector is in [`app/src/utils/server-protocol.ts`](https://raw.githubusercontent.com/anomalyco/opencode/3104c1428ec91f809e5ab86631300de41eb6952e/packages/app/src/utils/server-protocol.ts#L21-L30).

If the V2 spike is enabled after testing the actual server, its contract is `POST /api/session/:sessionID/prompt`, `GET /api/session/:sessionID/event?after=N`, and `GET /api/session/:sessionID/history?after=N`; the V2 HttpApi is explicitly annotated experimental (`0.0.1`).

The legacy `GET /event` stream is live-only. It registers an in-memory listener, filters by directory/workspace, emits `server.connected`, sends a heartbeat, and has no `after` cursor or replay path. A legacy reconnect therefore needs a live subscription plus a race-aware message/status/pending-request resync; a simple fetch followed by subscribe can miss events in between. Both the legacy and V2 server SSE encoders leave the SSE `id` field unset; the event ID is inside the JSON payload, so `Last-Event-ID` is not a supported recovery cursor.

## Runtime model and the phone boundary

OpenCode prompt execution is independent of the HTTP response in both relevant paths. V2 admission writes a durable inbox row/event, returns an admission receipt, and wakes execution unless `resume=false`; an exact retry with the same client message ID returns the same admission, while reuse with a different prompt/session/delivery conflicts. Legacy `POST /session/:sessionID/prompt_async` starts `prompt` in a forked scope, returns HTTP 204 immediately, and publishes an error event if the background prompt fails. A phone can therefore submit, disconnect, and later reconstruct the result.

For duplicate sends, generate and persist one message ID before the first V2 request. Retry the same request with that ID after a timeout; never generate a new ID until the server has proved that the first attempt was rejected before admission. The legacy prompt schema also accepts an optional `messageID`, but its handler creates/updates the message and loops directly; this research did not verify legacy duplicate behavior as an idempotent operation. Treat V2 as the duplicate-safe contract.

The phone and desktop/TUI share a live session only when they attach to the same OpenCode server process/endpoint. The TUI source uses an in-process worker and internal fetch/events by default; with external network options it obtains a server URL and uses that transport. OpenCode's local execution implementation creates a process-local run coordinator. A second `opencode serve` process may see persisted SQLite/session projections, but it does not share the first process's active runner, permission wait, or cancellation coordinator; concurrent use of one session across separate processes is therefore not a supported live-session design. Run one reachable headless server for the TUI and iPhone when live sharing matters.

## Recommended iOS state machine

Persist, per server identity and session ID, the last applied V2 durable sequence when the V2 spike is enabled, the last known projected message state, and locally generated but not yet acknowledged message IDs. Treat the server as authoritative; local state is a rendering cache.

While the scene is foreground-active:

1. Probe the server using the same health semantics as the official detector. Start with the legacy contract; only enter a separately tested V2 path when the installed runtime is proven to support it.
2. Start the legacy `/event` request and buffer events as soon as the stream is established, then fetch session metadata, messages, status, and pending permission/question requests. Apply the snapshot, replay the buffered events through an idempotent reducer, and do one final reconciliation read. A fetch-then-subscribe sequence can miss an event between those operations because legacy `/event` has no cursor; this buffer-and-reconcile sequence narrows the race but cannot provide a strict lossless guarantee.
3. For a V2 spike, pass `after=lastDurableSeq`; apply events in sequence order and persist the sequence only after the reducer has committed the event. V2 catch-up is durable-only; token/reasoning/tool-input delta fragments are explicitly live-only, while full `text.ended`, `reasoning.ended`, and tool settlement events are durable. A reconnecting UI must rebuild from projected messages/context and terminal durable values rather than assume every delta will replay.
4. On `server.connected`, malformed event, stream error, or server restart, repeat the appropriate snapshot/reconciliation. With V2, a sequence gap or failed cursor request should fall back to finite history plus projected-message resync.

Do not tear down the stream on every inactive transition: Control Center, an authentication prompt, or an incoming interruption can make a scene inactive briefly. Keep the foreground stream through transient inactive state, then on actual `sceneDidEnterBackground` cancel SSE, flush the message cache, and leave execution on the server. Do not try to keep a normal data-task SSE connection alive after suspension. On the next foreground transition, run the same resync-and-tail sequence; this handles suspension, termination, network/Tailscale changes, and a desktop client making progress while the phone was away.

## Pending questions and permissions

V2 has session-scoped list/get/reply routes for permissions and list/reply/reject routes for questions. On every foreground resync, query these lists and reconcile them by request ID; an event notification is only a wake-up hint. This reconstructs an approval prompt that arrived while the phone was suspended or disconnected. The legacy API has global pending list/reply routes for both permissions and questions, so a legacy client can also reconstruct them, but it must scope the returned records to the selected session itself.

Do not auto-reply because a stale local notification or a duplicate SSE event was received. Require the request ID to still exist in the current pending list, then send exactly one reply and remove it from local pending state only after a successful response. A 404 means the request was already answered or expired; resync before showing it again.

## What requires another component

Pure SwiftUI/app work covers the reducer, REST client, SSE parser, sequence/message persistence, foreground resync, duplicate-send handling, pending-request UI, and local notifications generated after a foreground-observed completion.

The existing OpenCode server must remain running and reachable on the tailnet. Tailscale on iPhone is a connectivity prerequisite, not a background execution mechanism.

Reliable “finished while the app was closed” alerts require an always-on observer with outbound APNs access. The smallest extra component is a host/VPS bridge that subscribes to the OpenCode event stream, records the last notified durable sequence per session/device, and sends a silent or alert APNs push. APNs credentials belong in this trusted sender's secret store; do not ship an APNs signing key in the iOS app or distribute it to every user host. The bridge must deduplicate/coalesce pushes and never treat a push as the source of truth; the app still resyncs from OpenCode after launch. Without this bridge, the app can notify only when it is running or when iOS later grants it a refresh opportunity.

No extra backend is needed for foreground direct HTTP/SSE use, the legacy flow, V2 catch-up, prompt admission, or permission/question replies. A relay/API gateway is optional: direct Tailscale routing or an existing tunnel can solve reachability, while a custom gateway is useful only when a separate access policy or centralized APNs identity is desired.

## Apple lifecycle constraints

Apple says a background scene eventually becomes suspended and can be disconnected at any time; scene transitions are the place to save state and quiet activity. A normal `URLSession` data task is suitable for short interactive foreground requests, but it is not a guarantee for a long-lived SSE stream after suspension.

Background `URLSession` is designed for HTTP/HTTPS file uploads/downloads performed by a system process. Apple's documented limitations include that only file-based uploads are supported after app exit; this is not a mechanism for maintaining OpenCode SSE or executing a model turn on the phone. Use it only if a future feature transfers attachments or exported logs.

Silent APNs background notifications (`content-available`) may wake the app to fetch updates, but Apple describes them as low priority, not guaranteed, and throttled; the app has about 30 seconds to do work and call the completion handler. Apple also says the system may retain only the newest pending background notification and discards held notifications on force-quit. Therefore pushes can reduce latency to a refresh but cannot provide event delivery guarantees or replace durable OpenCode replay.

Sources: [Managing your app's life cycle](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle), [About the background execution sequence](https://developer.apple.com/documentation/uikit/about-the-background-execution-sequence), [URLSession](https://developer.apple.com/documentation/foundation/urlsession), [Downloading files in the background](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background), [background URLSession configuration](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background%28withidentifier%3A%29), [Pushing background updates to your App](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app), [Choosing Background Strategies for Your App](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app).

## Untested assumptions and acceptance tests

Untested: the user's installed OpenCode version may differ from v1.18.30; the V2 experimental routes may be disabled or evolve; Tailscale reachability and server authentication were not tested; no live server was started; and no test verified whether two separate processes can safely observe or mutate one SQLite session concurrently. Treat source behavior as a release-baseline contract, then verify the actual installed server before shipping.

Acceptance tests:

1. Start one reachable server and attach desktop/TUI plus iPhone to the same endpoint; send from each and prove both render the same ordered session.
2. Submit a V2 prompt with a fixed message ID, terminate the phone connection immediately, retry with the same ID, and prove exactly one user message and one model turn.
3. Disconnect the phone during text/reasoning deltas, reconnect with `after`, and prove durable terminal events plus a projected-message resync produce the complete final response without duplicated text.
4. Leave a prompt running while the app backgrounds/terminates, then foreground and prove status, messages, pending permission/question requests, and sequence catch-up are correct.
5. Answer one permission and one question from the phone while the desktop is open; verify the pending request disappears once and the same session continues.
6. With legacy-only capability, establish `/event` and its buffer before the snapshot, force a reconnect, and prove buffered events plus the final reconciliation read leave message/status/pending-request state correct; document that strict losslessness is unavailable without a server cursor.
7. If push is included, delay/drop/coalesce pushes and force-quit the app; prove the next foreground resync remains correct and no push causes a duplicate prompt/reply.
